# Plan: lift Node API compat from 83/167 (49.7%) to >=117/167 (70%) and package matrix from 92/111 to >=95/111

Date: 2026-11-12. Baseline: node-compat.json (Node 22.0.0, total 167, pass 83, fail 83, skip 1) and package-matrix.json (111 packages, 19 non-pass). Goal needs +34 node test passes and +3 package passes.

## Ground rules

Skips do not raise the pass count (167 total is fixed by the manifest), so every counted gain must be a real pass. Canary tests (apps/compat-harness/src/canaries.ts) must keep failing or the run is invalid. The harness deliberately leaves genuinely native internals (internal/test/binding, internal/linkedlist, internal/timers) unresolved so those tests fail honestly; we only close gaps where a faithful JS implementation exists, mirroring how internal/event_target and internal/util are already shimmed in apps/compat-harness/src/test-common.ts.

A maki session is already active on branch feat/compat-runtime (origin/main..feat/compat-runtime, commits 2bb642c..6fadd35). Its diff touches: packages/node-web-shims/src/{async_hooks,events,timers_promises,util,worker_threads}.ts and packages/runtime/src/node-timers.ts, plus packages/node-runtime-shims/src/{child-process-shim,http-shim,process-shim}.ts and packages/runtime/src/node-process-worker.ts. It covers timers core, process-exit, next-tick, async_hooks, stream-adjacent, worker_threads, child_process, and net/https constructors. None of the work packages below modify those files; where an item touches adjacent behavior already on that branch, it is flagged as merge-after-maki.

### Group 3: unresolved whole node: modules falling back to esm.sh, 16 tests

Est. +9 to +13.

## How the alternatives handle the same gaps

WebContainers (StackBlitz) and CodeSandbox nodebox both run a complete Node binary compiled to WebAssembly plus a syscall translation layer, so tls, dgram, cluster, child_process.spawnSync all work by carrying the real native implementations; they do not need per-module JS shims. That approach is not available to bolo, which is V8-in-browser with Web API bridges, so the honest equivalent is explicit, behavior-correct JS modules plus explicit ERR_NOT_IMPLEMENTED throws for the surfaces that cannot exist (matching unenv's notImplemented pattern and the erroring-stub design of packages/node-web-shims/src/internal). almostnode follows the same V8-based strategy and publicly lists tls/dgram/cluster as unsupported, which is the gap this plan partially closes. Sources: [WebContainers overview](https://www.infoq.com/news/2021/07/webcontainers-nodejs/), [WebContainer API integration notes](https://blog.logrocket.com/integrating-the-webcontainer-api-with-node-js/), [nodebox-style browser Node runtime](https://github.com/dywangcloud/webcontainer).

## Verification

Each package runs pnpm build, pnpm test, pnpm typecheck, then the compat harness locally (cd apps/compat-harness and its run script) with the node filter for its touched modules, confirming canaries still fail and previously failing manifest files pass. The nightly compat-harness.yml workflow regenerates node-compat.json and package-matrix.json; a PR is only counted as progress when the regenerated JSON on main moves. No test may be removed from manifest.json to inflate the score, and expectations.json entries may only be removed when the test passes.
